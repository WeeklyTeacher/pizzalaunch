# Chef Book profile foundation

Status: Milestone 3 integrated foundation; source and native Studio acceptance are recorded in TEST_MATRIX. Tests described below execute production Luau through fake engine boundaries. No live profile store or analytics endpoint was exercised.

## Ownership and economy

`ProfileService` owns durable mastery and earned appearance. It never imports GameService, RecordRunService, TakeoutRunner, launcher policy, world geometry, or session inventory. The integration calls it only after a server has accepted a delivery, takeout completion, completed Record Run, or first launch. Profile notifications use a separate profile snapshot channel; they must never invoke the launcher's GameState presentation handler.

Coins, rounds, and the four upgrades remain shift-only. No balance, upgrade level, reload, power, hitbox, aiming, queue priority, or Record Run result is read from a profile. `PizzaLaunch_RecordRun_AllTime_v1` and its numeric historical scores remain untouched. Chef Book record milestones count completed runs observed after this system is added; they do not migrate or rewrite historical records.

`MasteryConfig` defines seven counters, six table stamps, twelve customer stamps, four internal earned nameplate styles, and personal record milestones. Appearance keys `plain`, `basil`, `tomato`, and `gold` are internal keys, not asset or product IDs. The catalog has no paid rewards, prices, products, sale prompts, timers, streak penalties, or random rewards.

## Stored document

Ordinary DataStore: `PizzaLaunch_PlayerProfile_v1`, key `u_<userId>`.

The versioned document contains `schemaVersion`, `revision`, creation provenance, optional session lease, and `data`:

- `mastery`: deliveries, perfect, great, farDeliveries, takeout, recordRuns, recordBest.
- `tableStamps` and `customerStamps`: bounded sets of server-observed service destinations/identities.
- `earnedCosmetics`, `equipped`, `tutorialCompleted`.
- `pendingFulfillment`: preserved reserved data only. This module exposes no purchase, receipt, entitlement, or fulfillment API.

Unknown serializable extension data is preserved. The validator rejects malformed required fields, invalid numbers/sets, excessive nesting/size, and future schema versions. It never repairs corrupt saved data by replacing it with defaults. Version 1 is the first profile schema; no migration from the competitive store or a previous profile schema exists.

## API for GameService integration

```luau
local profiles = ProfileService.new({
    onChanged = function(player, snapshot)
        -- Send through a dedicated profile RemoteEvent.
    end,
    onEvent = function(player, eventName, reason)
        -- Bounded lifecycle analytics only.
    end,
})
profiles:start()
profiles:addPlayer(player)
```

| Method | Required trusted input |
| --- | --- |
| `recordDelivery(player, receipt)` | `{sequence, tableId, accuracy, customerName?}`; table 1–6; accuracy `PERFECT!`, `GREAT!`, or `DELIVERED!`; optional catalog customer name |
| `recordTakeout(player, receipt)` | `{sequence}` after a consumed/awarded takeout completion |
| `recordCompletedRun(player, receipt)` | `{sequence, score}` from the immutable completed server run |
| `completeTutorial(player)` | Call after the first server-accepted launch; repeated calls do nothing |
| `equip(player, cosmeticId)` | The only appearance request; validates current profile state, catalog membership, and earned ownership |
| `snapshot(player)` | Deep copy of public mastery/appearance and persistence status |
| `removePlayer(player)` | Detach notifications immediately, then attempt serialized final save/release |

Each receipt domain has its own strictly increasing positive integer `sequence`, generated by the server and reset on a new ProfileService player session. Duplicate or older receipts do nothing. Never forward a client-supplied score, sequence, hit, table, identity, or reward into these methods. An adapter should increment its receipt sequence only on the existing authoritative success callback, preserving the same sequence if it retries that callback. This avoids an unbounded in-memory receipt-ID set.

The public snapshot contains `status`, `isNew`, `durable`, `persistenceAvailable`, `dirty`, mastery/stamps, earned styles, equipped style, and tutorial completion. It excludes session tokens, revisions, pending fulfillment data, and storage metadata. `isNew` is true only after confirmed creation, false after confirmed existing-profile acquisition, and absent for loading/failure/Studio memory mode.

Statuses: `loading`, `ready`, `memory`, `loadFailed`, `locked`, `malformed`, `unsupported`, `saveFailed`, `leaseLost`, and `unavailable`. Failed loading must never be displayed as a confirmed new chef. Keep normal gameplay available, and tell players plainly when Chef Book progress is currently limited to this visit or waiting to save.

Observer events are `ProfileLoaded` (`new`, `existing`, `memory`), `ProfileLoadFailure`, and `ProfileSaveFailure`. Failure reasons use a bounded enum; raw backend errors, player names, user IDs, GUIDs, and receipt IDs are not analytics dimensions. Observers receive copies and errors are contained; they should not yield or modify gameplay authority.

## Saving and concurrency

Acquire uses one `UpdateAsync` to read/validate the complete profile and claim a unique 120-second session lease. A second server cannot acquire an unexpired foreign lease. A retry after an uncertain acquisition response uses the same session token, so it can confirm its own prior successful acquisition. The store is never loaded through a cache-dependent `GetAsync` before ownership is established.

Autosave/lease renewal runs approximately every 30 seconds with per-player jitter. Operations serialize per user key within a server, including a rapid same-server rejoin while departure saving remains in flight. Different user keys may save concurrently. Callbacks read the current clock on every invocation, including backend retries, so a request cannot renew expired ownership using an earlier timestamp. A locally expired lease is treated as unconfirmed: a lost renewal response may have extended the backend lease, and only the atomic backend transform can declare ownership lost. Late acquisition callbacks after a departure deadline cannot create a new lease; they may only clear an existing lease bearing that same token.

Every save captures a deeply frozen data snapshot and revision before yielding. Retries reuse that exact snapshot. A successful response acknowledges only its revision; later mutations stay dirty and receive another write. Counters/bests cannot decrease; stamps, completed tutorial, and earned cosmetics merge monotonically. Equipped appearance is the requested earned choice. Repeated writes are idempotent, including requests that reached storage but returned an error.

Loading-period server-earned progress stays separate from unknown history. Only a successful acquisition merges those gains once into the loaded data. Failed/locked/malformed/future-schema loads cannot issue normal saves. Profile ownership loss fences all future writes from that session; normal gameplay and session observations can continue. This implementation does not automatically reacquire lost ownership and replay uncertain increments, because that could duplicate progress.

Final save releases the lease atomically with the saved revision. A release receipt in the same document recognizes a retried release after a lost success response. It cannot authorize a stale release once a new session owns the document. Shutdown and departure drains use a 25-second deadline with bounded retry delays. They do not submit partial active Record Runs.

Studio and unpublished places use an internal in-memory adapter automatically. This cannot be overridden by an injected store provider. No real profile DataStore is accessed even if Studio API access happens to be enabled. Memory profiles can rejoin within the same test server, but disappear with that server. No setting is enabled and nothing is published by these modules.

## Validation and remaining limits

Passing local evidence: 18 pure ProfileModel behavioral tests and 14 actual ProfileService tests with deterministic scheduling/shared fake backend. These cover malformed/new/locked loads, frozen revisions, lost responses, repeated transforms, two-server fencing/takeover, expired in-flight requests, loading-time gains, departure during acquisition, same-server reconnect serialization, earned-only equip, snapshot isolation, bounded shutdown, late acquisition after departure, and recovery after a lost renewal response beyond the locally known lease expiry. Studio/unpublished tests verify zero real-provider calls.

NOT RUN: production DataStore throttling/budget behavior, live cross-server reconnect, real shutdown persistence, Creator Hub data inspection, physical-device Chef Book accessibility. Fake backends cannot establish live service availability. A complete backend outage, crash, or lease loss can lose unconfirmed session gains; old saved profiles remain protected. A reconnect may wait for the 120-second lease plus retry/backoff and service latency while normal gameplay continues. This is a persistence foundation, not authorization to publish or enable live testing.

## Sources and future monetization boundary

The design follows Roblox's guidance on ordered per-key requests, session locks, failed-load fallback protection, and periodic saves: [Implement player data systems](https://create.roblox.com/docs/cloud-services/data-stores/player-data-purchasing). `UpdateAsync` callbacks may repeat and cannot yield: [Data stores](https://create.roblox.com/docs/cloud-services/data-stores).

Future paid entitlements require separate explicit approval and ownership/rejoin QA. They must be guaranteed, server-owned, durable, restorable, and competitively neutral. The reserved field does not implement those guarantees by itself. Never sell Record Run entry/retries/time/score/assistance, launcher access or priority, upgrades, accessibility, session coins, luck, or randomized rewards. No IDs, paid products, passes, purchase prompts, or displayed prices are created here.
